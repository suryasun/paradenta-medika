# task-324: Cancel Invoice

**Epic:** Billing Module Completion, Stage 1 (`docs/06-tasks/epic-billing-completion.md`)
**Module:** Billing
**Priority:** P1 - High

---

## Business Goal

Implement UC-BIL-014 "Cancel Invoice" (`docs/03-sad/16-module-billing.md` L1860–1869): let staff cancel an Invoice that was generated by mistake or is no longer needed — but only before any payment has been recorded against it, per the SAD's explicit precondition ("Only if no payment yet"). Today there is no way to undo an auto-generated Invoice at all; the only status transition that exists moves forward (UNPAID → PARTIALLY_PAID/PAID → CLOSED).

## Depends On

- task-054 (Generate Invoice), task-057 (Create Payment — the precondition this task checks against)

## Required Documents

- **SAD:** `docs/03-sad/16-module-billing.md` UC-BIL-014 (L1860–1869: "Only if no payment yet. Audit wajib."), Part 2 §9 State Machine (L1303–1362, documents a `Draft → Cancelled` transition; this codebase's Invoice starts directly at `UNPAID` rather than `Draft`, so this task's transition is `UNPAID → CANCELLED`, not `Draft → Cancelled` — an intentional adaptation to the shipped model, not a doc contradiction)
- **Business Rules:** `docs/01-prd/business-rules.md` §5

## Required Existing Code

`InvoiceStatus` enum (`schema.prisma`), `CloseInvoiceUseCase.ts` (the closest existing precedent for a terminal-status-transition use case), `IInvoiceRepository` (needs a new status-transition method, or reuse `updatePayment`'s status-setting shape).

## Backend Scope

- `InvoiceStatus` enum gains `CANCELLED`.
- New `CancelInvoiceUseCase.ts`: input `{ invoiceId, reason, actorUserId }`. Guards: Invoice exists, `status === 'UNPAID'` and `paidAmount === 0` (reject otherwise — "no payment yet" per SAD; if `PARTIALLY_PAID`/`PAID` already, staff must use Void, task-325, instead). Sets `status: 'CANCELLED'`, records `reason` (new `Invoice.cancelReason` column) and `cancelledBy`/`cancelledAt`. Audit-logs (mandatory per SAD).
- New `IInvoiceRepository.cancel(id, { reason, cancelledBy })` method (sibling to the existing `close` method).
- New permission `billing.invoice.cancel`.
- New route `POST /billing/invoices/:id/cancel`.
- A CANCELLED Invoice must be excluded from (or clearly marked in) any "outstanding" aggregation — check `sumOutstandingByBranch` (`InvoiceRepository.ts`) already scopes to `UNPAID`/`PARTIALLY_PAID` only, so CANCELLED is naturally excluded with no change needed there — confirm this during implementation rather than assuming.

## Frontend Scope

- `InvoiceDetailView.tsx`: "Cancel Invoice" action (confirm + mandatory reason, mirroring the `QueueReasonModal` pattern already used elsewhere in this codebase) shown only when `status === 'UNPAID'` and `paidAmount === 0` and permitted.
- `InvoiceListView.tsx`: `CANCELLED` gets its own status badge tone.

## Database Impact

Additive migration: `InvoiceStatus.CANCELLED`, `Invoice.cancelReason`/`cancelledBy`/`cancelledAt` (nullable).

## API Impact

New `POST /billing/invoices/:id/cancel`.

## Workflow Impact

New terminal status `CANCELLED`, reachable only from `UNPAID` with zero payments. No further transitions out of `CANCELLED` (terminal, matching `CLOSED`'s existing terminality).

## Security Impact

New permission `billing.invoice.cancel`. Mandatory reason + audit trail, per SAD.

## Testing Required

- Unit: `CancelInvoiceUseCase` — cancels a zero-payment UNPAID Invoice; rejects if `paidAmount > 0`; rejects if already CANCELLED/CLOSED/VOID.
- Integration: cancelled Invoice excluded from outstanding-balance aggregation.

## Deliverables

Migration, `CancelInvoiceUseCase.ts`, route, frontend UI, tests.

## Acceptance Criteria

- An UNPAID Invoice with zero payments can be cancelled with a mandatory reason.
- An Invoice with any payment recorded cannot be cancelled (must be Voided instead, task-325).
- CANCELLED is terminal — no further status transitions.

## Definition of Done

Cancel Invoice shipped end-to-end, tests passing, `business-rules.md` §5 updated.
